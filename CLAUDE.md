# LinkPulse — Claude Code Context

## Project Overview

**LinkPulse** is a URL shortener with an analytics dashboard, built as a portfolio project.
It demonstrates full-stack proficiency using the modern Next.js App Router ecosystem.

**Core value proposition:** shorten links, track clicks, visualize analytics — all in one place.

```
├── components/           # Reusable React components

├── next.config.ts        # Next.js configuration

```

### Key conventions

- **`src/app/`** uses the App Router file conventions: `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `route.ts` for API endpoints.
- **`lib/`** holds the Drizzle `db` client instance, NextAuth config, and any shared logic (slug generation, analytics helpers).
- **`types/`** contains shared interfaces and Drizzle-inferred types — prefer importing types from here over re-deriving them.
- **`components/`** — no sub-folder structure established yet; keep components flat until a clear grouping emerges.

## Database

**Provider:** Neon PostgreSQL (serverless, connection pooling via `@neondatabase/serverless`)
**ORM:** Drizzle ORM — schema defined in `lib/schema.ts` (or equivalent)

### Core tables (expected schema)

- `links` — `id`, `slug` (unique), `original_url`, `user_id`, `created_at`
- `clicks` — `id`, `link_id`, `clicked_at`, `ip`, `country`, `user_agent`, `referer`
- `users` — managed by NextAuth adapter

### Drizzle workflow

```bash
# Generate a migration after schema changes
npm run db:generate   # → drizzle-kit generate

# Push schema directly to Neon (dev only)
npm run db:push       # → drizzle-kit push

# Open Drizzle Studio
npm run db:studio     # → drizzle-kit studio
```

**Never edit files in `drizzle/` by hand** — they are auto-generated.

## Coding Conventions

- **TypeScript strict mode** is on — no `any` unless absolutely necessary and commented.
- **Server Components by default** in App Router. Add `"use client"` only when you need interactivity, browser APIs, or hooks.
- **Drizzle queries** belong in `lib/` or co-located server actions — never in Client Components.
- **Server Actions** preferred over separate API routes for form mutations.
- **Tailwind only** for styling — no inline styles, no CSS modules unless there's a compelling reason.
- **Named exports** for components; default exports only for page/layout files (Next.js convention).
- Keep components small and single-purpose. If a component exceeds ~150 lines, consider splitting it.

## Architecture Mental Model

```
Browser
  └── Next.js App Router
        ├── Server Components  →  fetch data directly via Drizzle
        ├── Client Components  →  UI interactivity only
        ├── Server Actions     →  mutations (create link, delete link)
        └── Route Handlers     →  /api/* (redirect logic, webhooks)

Redirect flow:
  GET /:slug  →  middleware or catch-all route
              →  query `links` table by slug
              →  log click to `clicks` table (async, non-blocking)
              →  redirect(301) to original_url
```

The redirect must be **fast** — avoid any synchronous side effects on the hot path.
Click logging should be fire-and-forget (e.g., `waitUntil` or background job).
